⚙️ Initial Setup & Configuration

1 Install Dependencies

Install the required testing dependencies:

npm install -D vitest @vitejs/plugin-react jsdom
npm install -D @testing-library/react @testing-library/jest-dom
npm install -D @testing-library/user-event

📌 What Each Package Does:

  • vitest - Fast test runner powered by Vite
  • @vitejs/plugin-react - React support for Vite
  • jsdom - DOM implementation for Node.js
  • @testing-library/react - React testing utilities
  • @testing-library/jest-dom - Custom Jest matchers for DOM

2 Create Vitest Configuration

Create vitest.config.js at the project root:

import { defineConfig } from "vitest/config";
import path from "path";

export default defineConfig({
  test: {
    environment: "jsdom",        // Simulates browser environment
    setupFiles: "./test/setup.js", // Global test setup
    globals: true,                // Enable global test APIs (describe, it, expect)
  },
  resolve: {
    alias: {
      "@": path.resolve(__dirname, "./src"), // Path alias support
    },
  },
});
Important: The resolve.alias configuration is crucial for making @ imports work in tests, matching your Next.js path configuration.

3 Create Global Test Setup

Create test/setup.js:

import { afterEach } from "vitest";
import { cleanup } from "@testing-library/react";
import "@testing-library/jest-dom/vitest";

// Set up environment variables for testing
process.env.NEXT_PUBLIC_SUPABASE_URL = "https://test.supabase.co";
process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY = "test-anon-key";

// Automatically unmount and cleanup DOM after each test
afterEach(() => {
  cleanup();
});

📌 Why This Setup Is Important:

  • cleanup() - Prevents memory leaks by unmounting components after each test
  • Environment variables - Required for Supabase initialization in tests
  • jest-dom matchers - Adds helpful assertions like toBeInTheDocument()

4 Add Test Scripts to package.json

{
  "scripts": {
    "test": "vitest",              // Watch mode (runs on file changes)
    "test:ui": "vitest --ui",      // Visual UI for tests
    "test:run": "vitest run"       // Run once and exit (CI/CD)
  }
}

📦 Import Patterns & Module Resolution

Critical Lesson: React Imports in Test Environment

Common Error: Even though Next.js 13+ auto-imports React, Vitest requires explicit React imports in test files.
❌ WRONG - Will Fail in Tests
// Component file
import { useState } from "react";

function MyComponent() {
  return <div>Hello</div>;
}
✅ CORRECT - Works in Tests
// Component file
import React, { useState } from "react";

function MyComponent() {
  return <div>Hello</div>;
}

Test File Import Pattern

Every test file should follow this import structure:

// 1. React import (if testing components/JSX)
import React from "react";

// 2. Testing utilities
import { render, screen, waitFor } from "@testing-library/react";
import { describe, it, expect, vi, beforeEach } from "vitest";

// 3. Component/module being tested
import MyComponent from "../MyComponent";

// 4. Additional dependencies (Redux, Router, etc.)
import { Provider } from "react-redux";
import { configureStore } from "@reduxjs/toolkit";

Path Alias Resolution

Use @ for imports consistently:

// ✅ CORRECT - Use path alias
import { supabase } from "@/lib/supabase/supabase";
import MyComponent from "@/components/MyComponent";

// ❌ WRONG - Relative paths can break in tests
import { supabase } from "../../lib/supabase/supabase";
Exception: When importing the module being tested, use relative paths (e.g., import Component from "../Component") as the test file is in the same directory structure.

🎭 Mocking Fundamentals

Understanding vi.mock()

Vitest's vi.mock() is automatically hoisted to the top of the file, before any imports are processed.

Basic Mock Structure

import { vi } from "vitest";

// This mock is hoisted to the top automatically
vi.mock("@/lib/supabase/supabase", () => ({
  supabase: {
    auth: {
      getSession: vi.fn(),
      onAuthStateChange: vi.fn(),
      signOut: vi.fn(),
    },
  },
}));
Critical Rule: Never use variables defined outside the mock factory function. They won't be available due to hoisting.
❌ WRONG - Variable Not Available
const mockAuth = {
  getSession: vi.fn(),
};

// This will fail - mockAuth is not defined yet
vi.mock("@/lib/supabase/supabase", () => ({
  supabase: { auth: mockAuth }
}));
✅ CORRECT - Define Inside Factory
vi.mock("@/lib/supabase/supabase", () => ({
  supabase: {
    auth: {
      getSession: vi.fn(),
      onAuthStateChange: vi.fn(),
    }
  }
}));

Accessing Mocked Module

To access and modify mocks in tests, import the module as a namespace:

import * as supabaseModule from "@/lib/supabase/supabase";

describe("My Test", () => {
  it("should do something", () => {
    // Access the mocked methods
    supabaseModule.supabase.auth.getSession.mockResolvedValue({
      data: { session: null },
      error: null,
    });
    
    // Run your test
  });
});

📌 Why Use Namespace Imports:

  • Provides access to mocked methods at runtime
  • Works with Vitest's module mocking system
  • Allows per-test mock configuration
  • Avoids issues with require() and path aliases

Mock Functions

Creating Mock Functions

// Simple mock function
const mockFn = vi.fn();

// Mock with return value
const mockFn = vi.fn().mockReturnValue(42);

// Mock with resolved promise
const mockFn = vi.fn().mockResolvedValue({ data: "result" });

// Mock with implementation
const mockFn = vi.fn((x) => x * 2);

Asserting on Mocks

// Check if called
expect(mockFn).toHaveBeenCalled();

// Check call count
expect(mockFn).toHaveBeenCalledTimes(3);

// Check arguments
expect(mockFn).toHaveBeenCalledWith("arg1", "arg2");

// Check last call
expect(mockFn).toHaveBeenLastCalledWith("lastArg");

Clearing and Resetting Mocks

import { beforeEach, vi } from "vitest";

describe("My Tests", () => {
  beforeEach(() => {
    // Clear call history but keep implementation
    vi.clearAllMocks();
    
    // Or reset everything including implementation
    vi.resetAllMocks();
  });
});

🌐 Testing API Routes

Next.js Route Handler Testing

Testing Next.js API routes requires understanding the Request/Response pattern:

src/app/api/test/__tests__/route.test.js
import { describe, expect, it } from "vitest";

// Mock Next.js request
const createMockRequest = () => ({
  url: "http://localhost:3000/api/test",
  method: "GET",
  headers: new Headers(),
});

describe("API Route: /api/test", () => {
  it("should return a successful response", async () => {
    // Import the route handler dynamically
    const { GET } = await import("../route.js");

    const mockRequest = createMockRequest();
    const response = await GET(mockRequest);

    expect(response).toBeInstanceOf(Response);
    expect(response.status).toBe(200);
  });

  it("should return JSON data", async () => {
    const { GET } = await import("../route.js");
    
    const mockRequest = createMockRequest();
    const response = await GET(mockRequest);
    
    // Parse JSON response
    const data = await response.json();
    
    expect(data).toHaveProperty("message");
    expect(data.message).toBe("Hello World");
  });
});

📌 Key Concepts:

  • Dynamic Import - Import route handler inside test to ensure clean state
  • Mock Request - Create request objects matching Next.js structure
  • Response Testing - Check status, headers, and body content
  • Async/Await - Route handlers are always async

Testing Different HTTP Methods

describe("API Route: /api/users", () => {
  it("should handle GET requests", async () => {
    const { GET } = await import("../route.js");
    const response = await GET(createMockRequest("GET"));
    expect(response.status).toBe(200);
  });

  it("should handle POST requests", async () => {
    const { POST } = await import("../route.js");
    const request = createMockRequest("POST", {
      name: "John Doe",
      email: "john@example.com"
    });
    const response = await POST(request);
    expect(response.status).toBe(201);
  });
});

🔄 Testing Redux Slices & Async Thunks

Testing Redux Reducers

Redux reducers are pure functions, making them straightforward to test:

src/lib/features/favourites/__tests__/favouritesSlice.test.js
import { describe, expect, it } from "vitest";
import favouritesReducer, {
  addFavouriteLocally,
  removeFavouriteLocally,
} from "../favouritesSlice";

describe("favouritesSlice reducers", () => {
  it("should return initial state", () => {
    const state = favouritesReducer(undefined, { type: "@@INIT" });
    
    expect(state).toEqual({
      favourites: [],
      loading: false,
    });
  });

  it("should add favourite locally", () => {
    const initialState = {
      favourites: [],
      loading: false,
    };

    const action = addFavouriteLocally({
      country_name: "France",
      flag_url: "france.svg",
    });

    const newState = favouritesReducer(initialState, action);

    expect(newState.favourites).toHaveLength(1);
    expect(newState.favourites[0].country_name).toBe("France");
  });

  it("should remove favourite locally", () => {
    const initialState = {
      favourites: [
        { id: 1, country_name: "France" },
        { id: 2, country_name: "Spain" },
      ],
      loading: false,
    };

    const action = removeFavouriteLocally({ country_name: "France" });
    const newState = favouritesReducer(initialState, action);

    expect(newState.favourites).toHaveLength(1);
    expect(newState.favourites[0].country_name).toBe("Spain");
  });
});

Testing Async Thunks

Async thunks require mocking external dependencies and testing different states:

import { describe, expect, it, vi, beforeEach } from "vitest";
import { configureStore } from "@reduxjs/toolkit";
import favouritesReducer, { fetchFavourites } from "../favouritesSlice";

// Mock Supabase
const mockSupabase = {
  from: vi.fn(),
};

vi.mock("@/lib/supabase/supabase", () => ({
  supabase: mockSupabase,
}));

describe("fetchFavourites async thunk", () => {
  let store;

  beforeEach(() => {
    vi.clearAllMocks();
    
    // Create a fresh store for each test
    store = configureStore({
      reducer: {
        favourites: favouritesReducer,
      },
    });
  });

  it("should fetch favourites successfully", async () => {
    // Mock successful response
    mockSupabase.from.mockReturnValue({
      select: vi.fn().mockReturnValue({
        eq: vi.fn().mockResolvedValue({
          data: [
            { id: 1, country_name: "France", flag_url: "france.svg" },
            { id: 2, country_name: "Spain", flag_url: "spain.svg" },
          ],
          error: null,
        }),
      }),
    });

    // Dispatch the async thunk
    await store.dispatch(fetchFavourites("user-123"));

    // Check the state
    const state = store.getState().favourites;
    
    expect(state.loading).toBe(false);
    expect(state.favourites).toHaveLength(2);
    expect(state.favourites[0].country_name).toBe("France");
  });

  it("should handle fetch errors", async () => {
    // Mock error response
    mockSupabase.from.mockReturnValue({
      select: vi.fn().mockReturnValue({
        eq: vi.fn().mockResolvedValue({
          data: null,
          error: { message: "Database error" },
        }),
      }),
    });

    await store.dispatch(fetchFavourites("user-123"));

    const state = store.getState().favourites;
    
    expect(state.loading).toBe(false);
    expect(state.favourites).toEqual([]);
  });

  it("should set loading state during fetch", () => {
    // Create a pending promise
    mockSupabase.from.mockReturnValue({
      select: vi.fn().mockReturnValue({
        eq: vi.fn().mockReturnValue(
          new Promise(() => {}) // Never resolves
        ),
      }),
    });

    store.dispatch(fetchFavourites("user-123"));

    // Check loading state immediately
    const state = store.getState().favourites;
    expect(state.loading).toBe(true);
  });
});

📌 Testing Async Thunks - Key Points:

  • Mock External APIs - Mock Supabase, fetch, axios, etc.
  • Test All States - Pending, fulfilled, and rejected
  • Use Real Store - Create a store with configureStore for integration
  • Clear Mocks - Reset mocks between tests for isolation
  • Check State Changes - Verify loading flags and data updates

Mocking Supabase Chain Methods

Supabase uses method chaining, which requires careful mocking:

// Supabase query: supabase.from('table').select('*').eq('id', 1)

// Mock structure:
mockSupabase.from.mockReturnValue({
  select: vi.fn().mockReturnValue({
    eq: vi.fn().mockResolvedValue({
      data: [...],
      error: null,
    }),
  }),
});
Pattern: Each method in the chain returns an object with the next method. The final method returns a Promise with {data, error}.

Testing Async State Updates

React Context with async operations requires act() and timeouts:

it("should handle successful session retrieval", async () => {
  const mockSession = {
    user: { id: "user-1", email: "test@example.com" },
    access_token: "token-123",
  };

  supabaseModule.supabase.auth.getSession.mockResolvedValue({
    data: { session: mockSession },

  render(
    <AuthProvider>
      <TestComponent />
    </AuthProvider>
  );

  // Wait for the initial session to be processed
  await act(async () => {
    await new Promise((resolve) => setTimeout(resolve, 100));

  expect(screen.getByTestId("session")).toHaveTextContent("Has session");
  expect(screen.getByTestId("loading")).toHaveTextContent("Not loading");
});
Important: The act() wrapper ensures React state updates are processed. The timeout allows async operations (like useEffect) to complete.

Testing Callbacks and State Changes

it("should handle auth state changes", async () => {
  let authStateChangeCallback;

  supabaseModule.supabase.auth.getSession.mockResolvedValue({
    data: { session: null },
    error: null,
  });

  // Capture the callback function
  supabaseModule.supabase.auth.onAuthStateChange.mockImplementation(
    (callback) => {
      authStateChangeCallback = callback;
      return {
        data: { subscription: { unsubscribe: vi.fn() } },
      };
    }
  );

  render(
    <AuthProvider>
      <TestComponent />
    </AuthProvider>
  );

  // Wait for initial render
  await act(async () => {
    await new Promise((resolve) => setTimeout(resolve, 100));
  });

  // Simulate auth state change by calling the callback
  const newSession = {
    user: { id: "user-2", email: "newuser@example.com" },
    access_token: "new-token",
  };

  await act(async () => {
    if (authStateChangeCallback) {
      authStateChangeCallback("SIGNED_IN", newSession);
    }
  });

  // Wait for state update
  await act(async () => {
    await new Promise((resolve) => setTimeout(resolve, 100));
  });

  expect(screen.getByTestId("user")).toHaveTextContent("newuser@example.com");
});

📌 Key Patterns for Testing Supabase Auth:

  • Mock getSession - Return mock session data
  • Mock onAuthStateChange - Capture callback to trigger manually
  • Use act() - Wrap all state updates and async operations
  • Add timeouts - Allow useEffect hooks to complete
  • Test cleanup - Verify unsubscribe is called on unmount

✨ Best Practices & Common Pitfalls

Best Practices

1. Test Isolation

beforeEach(() => {
  vi.clearAllMocks();  // Clear mock history
  cleanup();           // Unmount components
});

2. Descriptive Test Names

// ✅ GOOD
it("should display error message when login fails", () => {});

// ❌ BAD
it("test login", () => {});

3. Test User Behavior, Not Implementation

// ✅ GOOD - Test what user sees
expect(screen.getByText("Welcome, John")).toBeInTheDocument();

// ❌ BAD - Test internal state
expect(component.state.username).toBe("John");

4. Use Testing Library Queries Correctly

Query Priority:

  1. getByRole - Accessible queries (best)
  2. getByLabelText - Form labels
  3. getByPlaceholderText - Input placeholders
  4. getByText - Text content
  5. getByTestId - Last resort

Common Pitfalls

1. Forgetting React Import

Error: "React is not defined"
Fix: Add import React from "react"; to test files and components

2. Not Wrapping Async State Updates in act()

Error: "Warning: An update to Component inside a test was not wrapped in act(...)"
Fix: Wrap state changes in act() 
// ✅ CORRECT
await act(async () => {
  await new Promise((resolve) => setTimeout(resolve, 100));
});

// ❌ WRONG
await new Promise((resolve) => setTimeout(resolve, 100));

3. Using require() with Path Aliases

Error: "Cannot find module '@/...' "
Fix: Use ES6 imports: import * as module from "@/..."

4. Not Mocking External Dependencies

Error: Tests fail or hang due to real API calls
Fix: Mock all external dependencies (Supabase, fetch, etc.)

5. Testing Implementation Details

Issue: Tests break with refactoring
Fix: Test behavior and output, not internal implementation

Performance Tips

  • Use test.concurrent for independent tests
  • Mock heavy dependencies (databases, APIs)
  • Avoid unnecessary DOM queries in loops
  • Use screen.debug() sparingly (it's expensive)

🔧 Troubleshooting Guide

Issue: "React is not defined"

Symptoms: Tests fail with ReferenceError
Solution: Add import React from "react"; to component and test files

Issue: "Cannot find module '@/...'"

Symptoms: Module resolution fails in tests
Solutions:
  1. Check vitest.config.js has correct alias configuration
  2. Use ES6 imports instead of require()
  3. Verify path is correct relative to src directory

Issue: "act(...) warning"

Symptoms: Warning about unwrapped state updates
Solution: Wrap async operations in act() 
await act(async () => {
  await new Promise((resolve) => setTimeout(resolve, 100));
});

Issue: Mocks not working

Symptoms: Mocked functions are not called or return undefined
Solutions:
  1. Ensure vi.mock() is at the top level
  2. Import module as namespace: import * as module
  3. Clear mocks with vi.clearAllMocks() in beforeEach
  4. Check mock path matches actual import path

Issue: Tests timeout

Symptoms: Tests hang or exceed timeout
Solutions:
  1. Mock all async operations (API calls, timers)
  2. Check for infinite loops in components
  3. Ensure promises resolve/reject in mocks
  4. Increase timeout: it("test", async () => {}, 10000)

Issue: Redux state not updating

Symptoms: State remains unchanged after dispatch
Solutions:
  1. Use await store.dispatch() for async thunks
  2. Check reducer is properly handling action
  3. Verify store configuration includes reducer
  4. Use store.getState() to inspect current state
